The nozzle operating map sweeps six back pressures through a converging-diverging duct and
prints one row per pressure. The last two rows have no shock, and the four gates pass.

```text
  p_back/p0   M_exit   shock x [m]      Cf
      0.90    0.325       0.6562    0.242
      0.80    0.368       0.7656    0.277
      0.70    0.420       0.8516    0.316
      0.60    0.493       0.9297    0.365
      0.30    2.123         none    0.857
      0.10    2.123         none    1.254

operating map written to operating_map.csv
--- nozzle operating map ---
  [PASS] [tripwire] choking: every choked row crosses Mach 1 at the throat
  [PASS] [tripwire] shock position: every internal-shock row matches the closed form
  [PASS] [tripwire] shock-free profiles: every shock-free row tracks the area-Mach relation
  [PASS] [tripwire] physical thrust: thrust coefficient finite and positive on every row
=== All gates passed: nozzle operating map. ===
```

One expression produces it. Condensed from
`examples/avionics_examples/cfd/nozzle_operating_map/main.rs`, with the print calls left out:

```rust
CfdFlow::study("nozzle operating map")
    .read::<FloatType>(&path, "p_back_over_p0") // one case per value in the CSV column
    .case(model_config::duct_case)              // bind each case to a solver config
    .march()                                    // march every case
    .reduce(model::map_row)                     // one report becomes one row
    .record(out_path())                         // write the table
    .gates(model::nozzle_gates())               // pass or fail checks on the rows
    .verdict()                                  // the table and the gate results, as data
```

## Which verb builds the cases?

`read` takes a column of a CSV file. `cases` takes a `Vec<T>` you built. `matrix` reads typed
rows from a CSV file. Each value becomes one case, and each case becomes one row.

## Which verb turns a case into a row?

When each row is a closed-form evaluation, `sweep` maps a function over the cases. The flight
envelope placard does this with no march at all (print calls left out):

```rust
CfdFlow::study("flight envelope placard")
    .matrix::<FlightPoint>(&matrix)
    .prepare(model_config::shock_model)   // build the shared apparatus once
    .sweep(model::placard_point)          // one closed-form row per point
    .record(model_config::table_path())
    .gates(model::placard_gates())
    .verdict()
```

When each row needs a solver march, `case` binds a config, `march` runs every case, and a
reduction turns each report into a row.

`reduce` maps one run to one row and runs per case. `reduce_all` receives every run at once and
runs sequentially. Use `reduce_all` when a row depends on other rows, such as a shared reference
point derived from one case that every other case scores against. The corridor derives its aim
point this way. `reduce` does not serialize the fan-out.

## The compiler enforces the order

Each verb exists only in the phase where it applies. `record` and `gates` need rows first, and
`verdict` needs a gating sequence first. Five `compile_fail` doctests on `CfdFlow::study` pin
this, including a `GateSeq<i32>` applied to `f64` rows. A mis-ordered study does not compile.

## The table is written before the gates run

`record` precedes `gates`, so a failed gate still leaves the table that shows why it failed. The
flight envelope placard shows it. With a matrix that violates the placard, the example exits 1
and still overwrites `placard_table.csv`.

## Sweeps run concurrently

`sweep` and `reduce` run cases concurrently under the `parallel` feature, which is on by
default. Without it they run inline. Results come back in case order in both modes. The VIV
example records a concurrent run that matches its sequential run bit for bit.
