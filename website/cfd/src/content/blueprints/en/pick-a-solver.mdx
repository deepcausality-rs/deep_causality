The problem class decides. Incompressible flow on a fixed mesh uses the DEC solver. A
compressible layer uses the QTT marcher. A stagnation line with no grid uses a closed-form
closure. A curved shock captured on Cartesian axes at high resolution has no supported family. The
[solvers page](/solvers/#which) defines the terms and tabulates each problem class with its
evidence.

One program shape covers all three families. The type of the config you pass to `CfdFlow::march`
selects the pipeline:

```rust
type FloatType = f64; // change to Float106 to rerun at 106-bit

// Incompressible flow on a fixed mesh: the DEC solver
let cavity = CfdFlow::march(&dec_config).run_owned()?;

// Compressible layer: the QTT marcher
let layer = CfdFlow::march(&compressible_config)
    .couple(coupling)
    .from_field(field)
    .run_for(steps)?;

// Stagnation line, no grid: a closed-form closure
let shock = FittedNormalShock::<FloatType>::new(lift(1.4))?;
let post = shock.post_shock(t_inf, n_inf, mach)?;
```

`MarchDispatch` resolves the pipeline from the config type at compile time. There is no runtime
solver registry and no dynamic dispatch.

## A curved shock on Cartesian axes needs another family

QTT compression depends on coordinate alignment, not on smoothness. A curved shock captured on
Cartesian axes costs more than a dense grid, and in 3-D the rank of the compressed field grows as
roughly the square root of the side length. Align the coordinate with the shock, or pick a
different family. The [limits page](/boundaries/#sqrt-side) has the measurements.

## The DEC solver keeps the field divergence-free

Each step projects the velocity update, so the field stays divergence-free. The
`SolenoidalField` type makes time-stepping an unprojected field a compile error, where the
alternative is a run that diverges slowly. The measured divergence residual on the wake case is
3.33e-15 against a 1e-6 tolerance.

## Precision is one alias

Every example carries one alias:

```rust
pub type FloatType = f64;
```

The physics is written against the scalar bound, so changing that line reruns the computation
at another precision. `f32`, `f64` and `Float106` are all supported. The
[precision page](/solvers/precision/) has the measurements: in the
[turbulence example](/examples/turbulence-flow/) the forecast horizon is 21.5, 44.5 and about
81 across the three.

`f32` also has a representability limit. An earlier build of the corridor crashed at `f32` at
step 1: a term in its ionization kernel evaluated to 4.4e-67, below the `f32` exponent range.
